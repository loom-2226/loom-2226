## BLUF

The Earth–Luna spatial slice is ready to hand to HUD/GIS and Navigator as a governed integration surface.

The generated Earth–Luna registry contains **40 named targets**:

- **31 WORLD-backed facilities**;
- **9 standard operational orbit targets**.

All 31 facilities have deterministic low-detail procedural 3D visual proxies plus symbolic fallback. The proxies are explicitly `VISUALIZATION_ONLY`, `NON_NAVIGATION`, `NON_CANON_GEOMETRY`, and use normalized presentation units rather than physical metres.

All nine standard orbits are state-resolvable through the existing shared parent-centric propagator using WORLD-backed Earth/Moon radius and GM plus the caller-supplied shared parent-body state service.

WORLD-backed conventional Keplerian orbital facilities are state-resolvable through the same shared spatial-state seam. Surface-fixed and rotating-frame/CR3BP facilities remain selectable/describable but intentionally fail closed for epoch-dependent state until their specialized shared frame resolvers are qualified.

Detailed station complexity remains deferred by design.

## Authority map

### WORLD SQLite

Owns:

- facility identity and names;
- facility classification and operational context;
- location/orbit model lineage;
- engineering classification;
- transport profile;
- Earth/Moon physical constants used by this slice;
- approved HERO media linkage through existing knowledge/media tables.

WORLD does **not** receive mutations from this work.

### SPATIAL_GEOMETRY runtime SQLite

Generated by `src/loom/spatial/geometry_catalog.py` from the committed seed plus read-only WORLD.

Owns only:

- Earth–Luna target registry;
- non-facility standard-orbit definitions;
- WORLD model bindings;
- symbolic presentation records;
- deterministic normalized procedural visual proxies;
- future extension points for render assets and operational geometry.

It explicitly does **not** own propagated physical state.

### Shared spatial/navigation services

Own:

- epoch-dependent position and velocity;
- orbital propagation;
- frame transforms;
- future surface body-fixed transforms;
- future CR3BP/rotating-frame resolution.

### HUD/GIS

Consumes scene/object contracts and owns presentation only:

- rendering;
- symbology;
- selection;
- labels;
- presentation scaling;
- HERO/details display.

HUD/GIS must not recompute target physics or treat procedural station proxies as physical/navigation geometry.

### Navigator

Consumes the same target router and shared `SpatialState` values as every other caller. It must not maintain a second Earth–Luna target catalog or alternate coordinates.

## Runtime build

Generate the runtime geometry/target database:

```bash
python -m loom.spatial.geometry_catalog \
  --world data/LOOM_2226.sqlite3 \
  --seed geometry/earth_luna_spatial_geometry_seed.sql \
  --output data/LOOM_2226_SPATIAL_GEOMETRY.sqlite3
```

The generated SQLite is a runtime/cache product and should not be hand-edited or treated as source authority.

## One-call runtime wiring

Use the existing shared parent-body state resolver as the only external state dependency:

```python
from loom.spatial import build_earth_luna_runtime

runtime = build_earth_luna_runtime(
    world_db_path="data/LOOM_2226.sqlite3",
    geometry_db_path="data/LOOM_2226_SPATIAL_GEOMETRY.sqlite3",
    body_state_resolver=shared_body_state_resolver,
)
```

The returned `EarthLunaRuntimeBundle` exposes:

- `body_properties` — read-only WORLD radius/GM adapter;
- `facilities` — WORLD-backed conventional facility resolver;
- `standard_orbits` — geometry-registry standard-orbit resolver;
- `router` — unified 40-target dispatcher;
- `hud_objects` — thin WORLD-backed facility object adapter;
- `scene` — HUD/GIS-ready Earth–Luna scene adapter.

## HUD / GIS integration

Build one single-epoch Earth–Luna scene:

```python
scene_payload = runtime.scene.build_scene(epoch_utc)
```

Contract:

`LOOM_EARTH_LUNA_SCENE_V1`

Current contents:

- 31 facility objects;
- 9 standard orbit objects;
- one explicit epoch;
- shared-state authority declaration;
- proxy-geometry authority declaration;
- station-detail deferral policy.

For conventional orbital facilities, the scene contains resolved shared `SpatialState`. For targets whose specialized resolver is not yet qualified, the scene retains the governed identity/metadata but does not invent a state.

A selected facility may also be read directly:

```python
obj = runtime.hud_objects.describe_object("EAR-O01")
resolved = runtime.hud_objects.resolve_object("EAR-O01", epoch_utc)
```

Contract:

`LOOM_HUD_SPATIAL_OBJECT_V1`

The object includes existing WORLD identity, facility type, authorities, engineering classification, transport role, approved HERO reference, geometry metadata, procedural visual proxy, and—when honestly resolvable—the exact shared spatial state.

## Procedural 3D visualization proxies

Every WORLD-backed Earth–Luna facility receives one deterministic `RENDER_LOW` proxy generated from its existing facility type.

Current archetypes include:

- habitat port;
- industrial/cargo port;
- service port;
- shipyard;
- rotating habitat;
- strategic/science/relay port;
- surface port;
- generic facility fallback.

Proxy components use simple renderer-friendly primitives such as torus, cylinder, box, sphere, and dish with normalized transforms.

Hard rules:

- `geometry_authority = VISUALIZATION_ONLY`;
- `navigation_authority = false`;
- `canon_geometry = false`;
- `scale_basis = NORMALIZED_PRESENTATION_UNITS`;
- `physical_scale_m = null`.

The HUD may presentation-scale these models for legibility. It must not interpret normalized sizes as metres, collision envelopes, docking geometry, berth counts, capacity, or engineering dimensions.

A later approved GLB can replace a procedural proxy without changing target identity or state authority.

## Standard orbit integration

All nine standard orbit definitions are now first-class registry targets and resolvable through `SQLiteStandardOrbitResolver`.

Examples:

- `ORB-EA-LEO-400`;
- `ORB-EA-GEO-REF`;
- `ORB-LU-LLO-100`;
- `ORB-LU-POLAR-100`.

The resolver:

1. reads the standard-orbit definition from SPATIAL_GEOMETRY;
2. reads Earth/Moon mean radius and GM through read-only WORLD `celestial_properties` / fallback `celestial_dynamics`;
3. obtains parent-body epoch state from the caller-supplied shared body-state service;
4. uses the existing `ParentCentricOrbitModel` / `propagate_parent_centric()` engine;
5. composes the parent-centric state into the shared `J2000/ECLIPTIC` state.

No duplicate production GM or radius constants are introduced.

These standard orbits remain engineering references and are explicitly non-navigation-grade.

## Navigator integration

Wrap the unified router in the existing Navigator adapter:

```python
from loom.navigation import NavigationTargetAdapter

nav_targets = NavigationTargetAdapter(runtime.router)

station_state = nav_targets.resolve_target_state("EAR-O01", epoch_utc)
parking_state = nav_targets.resolve_target_state("ORB-LU-LLO-100", epoch_utc)
```

`NavigationTargetAdapter` performs no orbital math. It returns the shared spatial layer's `SpatialState` unchanged.

Manual, LLM/Mara, NPC and system-planner consumers should resolve the same target ID through this same target seam.

## Deferred station complexity

The v0.1 policy remains:

- `detail_scope = THIN_WORLD_BACKED_V1`;
- `detail_policy = STATION_COMPLEXITY_DEFERRED`.

Explicitly deferred:

- exact physical station dimensions;
- detailed GLB station design;
- interior topology;
- berth/docking graphs;
- collision geometry;
- approach corridors;
- keep-out volumes;
- exact mass/pressurized volume;
- capacity/throughput/staffing derivation.

WORLD physical/energy/capacity schemas exist but are currently unpopulated for this facility corpus. Those should be enriched later through the existing WORLD schema rather than invented in HUD records.

## Known specialized-state gaps

These are intentionally not hidden by the handoff:

1. Earth/Moon `PARENT_BODY_FIXED` targets require a qualified shared body-fixed→inertial orientation transform.
2. Earth–Moon and Sun–Earth Lagrange-family facilities require qualified shared rotating-frame / CR3BP adapters.
3. Existing facility orbit models and standard orbit targets remain engineering-reference and non-navigation-grade until separately qualified.

These gaps do not prevent HUD/GIS from indexing, selecting, labeling and visually representing all 40 targets. They do prevent Navigator from pretending unresolved targets have valid ordinary-space state.

## Integration acceptance checklist

### HUD / GIS consumer

- Consume `LOOM_EARTH_LUNA_SCENE_V1` rather than querying physics tables directly.
- Render standard orbit rings from supplied definition/state semantics.
- Render facility proxy primitives from `geometry.visual_proxy.components`.
- Treat proxy scale as presentation-only.
- Place resolvable objects using supplied shared state; never derive browser coordinates from orbit fields.
- Keep unresolved facilities discoverable/selectable without manufacturing XYZ.
- Use existing HERO media and WORLD metadata for selection/details.
- Keep renderer materials/colors/label behavior on the HUD/GIS side.

### Navigator consumer

- Use `NavigationTargetAdapter(runtime.router)`.
- Accept registry IDs rather than hard-coded coordinates.
- Treat standard orbit and conventional facility states as engineering-reference/non-nav-grade unless a later qualification explicitly upgrades them.
- Allow unresolved surface/CR3BP targets to fail closed until specialized spatial services are available.
- Do not create a second target/state catalog.
