# ADR-001 — Publish immutable epoch scenes with semantic local refinement

Status: recommended for bounded prototype; production adoption awaits acceptance.
Class: engineering. Date: 2026-09-28. Authority/scope: [README](README.md).

## Decision

Compile a **fixed-epoch, immutable progressive scene package** offline from the
existing Solar registry/resolver. Publish a small manifest and root context,
followed by independently loadable system/geometry-level JSON chunks, compressed
with HTTP gzip. A flat node directory encodes a semantic system tree and tight
spatial bounds. Screen-space size admits local context; measured geometric error
selects curve resolution. Consumers use stable IDs, explicit geometry semantics,
Float64 local coordinates and camera-relative rendering. The QA viewer and future
Navigator consume the same files and shared loader/refinement contract.

The first product freezes 2226 TDB, not all future time. Dynamic state and route
solving belong to Navigator/Solar services. A later epoch requires another build;
clients cannot move epoch markers using reference orbit samples.

## Evidence and requirements

Current authority is 110 bodies, not a terrain or billion-object problem. At 2226,
seven identities are legitimately unresolved. Existing Q8 showed why global
worldlines are poor local cartography even when physically correct. The legacy
GIS staged bootstrap/geometry/details and Navigator compiled quantized tracks
before presentation. Those are useful publication principles. Their orbit
approximations and historic authority rules are unsuitable donors.

The measurement root projection is 22,713 raw / 5,736 gzip bytes before manifest,
provenance and root curves. Five 512-vertex curves each take roughly 30 KB JSON /
15 KB gzip, with host parse+Float64 conversion median 0.3 ms. Binary Float64
reduces these to 8.6–11.7 KB gzip but requires a second decoding/layout contract.
That saving is too small to justify it for this prototype. A 512-point master can
already be insufficient at close scale: simplifying a sampled polyline to itself
says nothing about physical motion between its samples. Separate sampling and
simplification validation is mandatory.

Current scale planning: 110 physical identities now. Legacy fixture includes 164
entities, of which 115 are infrastructure fixture entries. Treat 10^2–10^3 static
features as an engineering sizing scenario, NOT a forecast or canon inventory.
Record a 1,000-record metadata stress case as synthetic metadata only; do not
synthesize positions or add it to the published catalog. Larger content can use
more nodes without changing semantics. No up-front octree/service is justified.

## Competing designs and disposition

| Design | Result and reason |
|---|---|
| Single compact all-detail artifact | Good test/reference bundle, rejected as default: local high detail blocks useful context and all updates invalidate whole bundle. Root-only preview does not fix memory/load growth. |
| Query live resolver per camera/zoom | Rejected: duplicates expensive physical work and couples cheap clients to service state; current Inspector is intentionally a qualification instrument. |
| Semantic nodes + per-level gzip JSON | **Chosen**: fits body/system provenance, small cardinality, visible refinement and Navigator reuse. Static hosting/offline works. |
| Spatial octree/3D Tiles/I3S | Useful bounds/SSE/refinement principles; full schemas, geographic origins and publishing stacks are unnecessary here. Sparse systems and moving epoch choices are semantic first. Revisit spatial indexing inside a dense system only after evidence. |
| GLB per system | Useful later for body meshes/facilities; loses simplicity for double-precision timed provenance polylines. Needs extra metadata regardless. |
| Custom binary / CBOR / delta codec | Measurable saving, small at this scale. No codec or new dependency in prototype; versioned chunk media types reserve a later migration. |
| Legacy preprojected SVG screen tracks | Fast for fixed cameras but duplicates every view and prevents continuous 3D reuse. Reject as scene product contract. |

## Consequences

- Ordinary static HTTP server, no physical runtime on the publication host.
- Build cost becomes explicit; no promise that offline compilation is fast.
- Per-system JSON repeats a small amount of geometry between levels. This buys
  independent fetching, validation, eviction and rollback without delta chains.
- Camera transforms are newly permitted presentation behavior for this basemap.
  This does not modify the old Navigator's screen-primitive contract, its solver,
  or the Inspector. Navigator integration needs its own adapter qualification.
- No implicit time interpolation, orbit closure, texture/shape authority, dynamic
  vessel layer, campaign state, or automatic terrain infrastructure is introduced.
- Generic unresolved records remain present in the root index; spatial rendering
  is absent when no physical position exists. A catalog panel explains why.
- Viewer prototype may PASS on emulation only with an explicit qualification
  label. Physical Pixel acceptance remains required before production promotion.

## Review triggers

Reconsider serialization only if parse/upload or transfer dominates measured
refinement. Add spatial subdivision only when a populated node's measured
visibility work fails the acceptance budget. Add epoch bundles only when a
Navigator consumer defines temporal validity. Never solve these by adding browser
physics or borrowing old ungoverned coordinates.
