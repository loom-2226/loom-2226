# Production follow-on (outline only)

A successful prototype earns the publication architecture, not an automatic
production release or Solar Phase 5. Subsequent bounded work items:

1. Physical Pixel qualification over actual LOOM access path: touch/zoom, cache,
   sustained thermals/memory, frame/render behavior and readable uncertainty.
   Preserve emulation results separately. Requalify depth/precision with hardware.
2. Promote the product schema and loader API through normal engineering/runtime
   change control; register dependency/compatibility edges for compiler, published
   builds, QA and Navigator adapter. Revalidate downstream after source/spec changes.
3. Harden publication lifecycle: version retention, manifest integrity, interrupted
   build recovery, offline packages, cache eviction, content compression and access
   policy. No managed cloud service is intrinsically required.
4. Complete catalog curve coverage using exact existing authority and per-system
   policy; add body shape/radius/mesh only from independently governed sources.
   Broader time products require an explicit epoch validity contract and cost study.
5. Integrate Navigator as another consumer of the same artifacts/shared loader.
   Keep operational overlays and campaign state separate. Compare epoch/frame/
   authority and knowledge permissions before display; never consume a cartographic
   reference as a physical route or prediction. Test with a second adapter that
   has no QA-page dependency before claiming reuse complete.
6. Admit stations/habitats/facilities/routes only via their registered static spatial
   authority and classification/knowledge policies. Subdivide densely populated
   nodes when measured counts/visibility cost demand it, without replacing IDs or
   semantic parentage. Dynamic vessels remain separate simulation overlays.
7. Adopt binary/GLB/worker/spatial index only against an observed bottleneck and
   compatible contract version. Do not make anticipated infrastructure volume an
   excuse for premature format/platform complexity.

Any of these may require its own approval/qualification; this outline grants no
production implementation or merge authorization. Recovery always retains the
previous immutable build; authority data is never rolled backward by basemap rollback.
