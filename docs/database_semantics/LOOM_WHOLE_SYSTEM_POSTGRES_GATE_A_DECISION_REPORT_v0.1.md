**Classification rule.** `STRUCTURAL` means a source PK/FK component, verified endpoint, join discriminator or necessary temporal/derivation key; it is a candidate for typed relational preservation, never automatic acceptance of the relationship's meaning. `QUALIFIED` means field-specific evidence establishes definition, relevant unit/category, grain, epoch and applicable accounting/population basis **within the recorded row filter**. `UNRESOLVED` has field-specific evidence or a prior assessment but one of those dimensions remains insufficient. `NOT_ASSESSED` means the dictionary inventories storage but no completed field-specific Gate-A review is supplied. `NOT_APPLICABLE` is operational, lineage, media-workflow or technical metadata rather than a universe claim. Source SQL type, populated values, table-level recovery status and Phase 2B migration candidacy do not upgrade a field. A field whose literal value is also a relationship/type key has a separate `embedded_claim_status` in the matrix; unresolved literal values remain outside PostgreSQL pending a typed, evidence-backed design. Unknown definition/unit/grain/epoch/basis is recorded as `UNKNOWN`.

**WALTER / provenance — `REVIEW_REQUIRED`.** Phase 2A records a conflict between repaired dictionary and older dossier table-level labels for self-documenting registries. Under `data/AGENTS.md` and the interpretation contract, neither label qualifies a whole table. The matrix uses exact column evidence and records missing field evidence; reconcile any selected field before import acceptance.

## Structural preservation and largest gaps

Preserve original composite PKs, declared FKs, self-parent links, endpoints, temporal/scenario/sector/asset/mode discriminators, join tables, derivation/run IDs and source-hash lineage as typed candidates. Preserve a source relationship without narrating unqualified ownership, control, influence, legal force or population allocation. **Nineteen structural columns have unresolved literal/code meaning** in this review; such literals need a qualified vocabulary or an opaque typed key strategy before PostgreSQL value import. `entity_authorities`, `knowledge_relationships`, `civ_influence_edge`, `civ_actor_exposure`, `civ_country_institution_membership`, `civ_jurisdiction_recognition`, graph caches and transport links are particularly prone to false authority or direct-service claims. The census-node link's qualified code still never moves zone residents onto a facility. Source SQLite stays outside PostgreSQL for exact forensic recovery; no raw/quarantine schema is proposed.

The highest-impact **existing but unqualified** information is: WORLD orbit, ephemeris, frame, physical and placement fields outside the bounded Ceres physical reference; `civ_country_numeric_state.population` and age/micro-demographic summaries; facility workforce, capital/value added/cost/power/utilization; sector and asset allocation fields; institution relation basis/control/weight and political-score/narrative fields; social pressure and social-score meanings; and OD freight value/transit-time fields. Several have values or source columns, but the necessary field-specific unit, grain, epoch, accounting denominator, category anchors or producer contract is not recovered. Political breadth scores are gameplay scaffolds and may not allocate population, GDP, capital or migration. Existing source columns do not make these claims admissible.

**Absent or unsupported model capabilities are a different finding.** Within the assessed WORLD/CIVSTATE contracts, there is no mature endogenous cohort/household/activation history, household income/beneficial-ownership layer, literal engineering berth inventory, or scheduled direct-service/travel-time output; some corresponding SQL fields are deliberately NULL. This is not a claim that no other LOOM subsystem could ever supply those capabilities. The original Phase-13 gameplay generator remains unrecovered even though its checkpoint state survives. These gaps are not evidence that all historical values are absent, and they are not cured by renaming existing columns. Phase 2B's separate Earth empirical-output handoff, corrected country producer/replay and media release-asset verification questions remain open. No new forensic search or generator reconstruction was performed here.

Navigator runtime and graph consumers, mutable campaign state/history, and the separate media SQLite/release assets are **architectural lanes outside this 95-table matrix**. Their persistence, approval, release and rollback contracts require separate inventories before any PostgreSQL migration claim; they are not silently declared absent or covered by WORLD/CIVSTATE counts. The Phase 2B machine ledger preserves all 95 whole-system planning lanes and separate view accounting.

## Recommended first import and blueprint revision

The smallest **LOOM-wide** candidate import, once separately authorized, is: versioned source-artifact/model/semantic metadata with exact hashes; typed WORLD entity and knowledge-noun IDs and CIVSTATE subject IDs, parent links and only verified cross-database ID bridges; then the three globally qualified `civ_demographic_state` values for the **139 modeled 2226 BODY/NETWORK and census-zone rows**. Keep the 2226 macro-region rows and all unresolved descriptive columns outside PostgreSQL. The two resident categories and daily nonresident presence must stay separate; body and child-zone totals must not be blindly summed. This exercises whole-system IDs, time and one admitted value family without a Ceres `WHERE` clause. Country economics, infrastructure proxies, workforce and OD demand can follow as separately bounded typed slices; country `ROW`/reporting-unit treatment and historic/current model snapshots require explicit accounting and version handling before any aggregate claim. This is an import *recommendation*, not authorization or a completed data validation.

Revise the current Ceres-centric PostgreSQL blueprint precisely as follows: (1) make its first foundation migration and source/version registry **whole LOOM**, with an explicit field-and-row admission manifest generated from this matrix rather than the Ceres display allowlist; (2) move its Ceres-specific tables and 20 bounded descriptive fields into a downstream consumer projection, while retaining the 15 qualified dictionary-scope fields as candidates for their stated subjects and source/status as structural/control metadata; (3) add `NOT_ASSESSED` and row-filter states, preserving structural keys separately from semantic code meaning and preventing unresolved values from entering any generic payload; (4) make the first import the typed identity plus 2226 demography candidate above, with source SQLite outside PostgreSQL and B/C/D independently recorded; and (5) verify the live Atlas consumer revision only when integrating that later Ceres projection. Do not edit the old blueprint in this documentation task; its existing hashes and historical design decision remain intact.

**Validation:** the matrix has one entry per dictionary `(database, table, column)`, exactly 42 WORLD and 53 CIVSTATE tables, all 1,014 columns, and one matching Phase 2B record per table. Status totals and the domain table above reconcile. Every `QUALIFIED` descriptive entry has a non-UNKNOWN definition, unit/category, grain, temporal basis and population/accounting basis; every `UNRESOLVED`/`NOT_ASSESSED` entry states missing evidence. No SQLite or source artifact was changed and no functional test was needed for this documentation-only assessment.
