## Development target and data coverage

The isolated target is PostgreSQL `loom_dev`, snapshot `ceres-v1-0231e5f7da744728ab5021268b6f239b`, state `VALIDATED`. The [foundation migration](../../data/postgres/migrations/001_ceres_complete.sql), [lineage migration](../../data/postgres/migrations/002_ceres_lineage_semantics.sql) and [qualification-scope migration](../../data/postgres/migrations/003_ceres_qualification_scope.sql) create `loom_control`, `loom_world`, `loom_civ`, `loom_media`, and `loom_ceres`. The first four hold versioned typed source concepts and keys for a whole-LOOM architecture. `loom_ceres` provides read-only, snapshot-selected compatibility views for this first consumer. A session must set `loom.snapshot_id`; the running SQLite-backed service has no PostgreSQL binding.

The [importer and verifier](../../tools/ceres_pg.py) preserved **518 exact selected SQLite rows** in **21 typed tables**: 26 WORLD, 486 CIVSTATE and six MEDIA. This includes all source columns returned by the Atlas `SELECT *` queries, all six original image blobs, three zones, 40 social-pressure rows, 11 census-node links, all 55 Ceres source influence edges, 349 required subject rows, model-run/derivation records and structural ancestors. The Atlas's present edge filter projects 25 of those 55; the other 30 historical-lineage edge records remain in PostgreSQL without being assigned a new display meaning. Five 14-field manifest records and their 11 nested zone relations are also present. **534 exact source-key lineage entries** link every imported row and normalized manifest relation to its source artifact hash; all 59 foreign keys are validated.

## Repeatability, restore and scope limits

Running the import a second time selected the same snapshot and reverified all coverage without inserting duplicate source rows. The [unit and integration tests](../../tests/test_ceres_pg.py) passed (4/4), including the actual consumer query-payload comparison against PostgreSQL. The [backup/restore tool](../../tools/ceres_pg_backup_restore.py) dumped the five development schemas, restored them into a disposable database, reran the full comparison and dropped only that disposable database. The [restore result](LOOM_CERES_POSTGRES_DEV_BACKUP_RESTORE_v0.1.json) is PASS; the retained backup is `/tmp/loom_ceres_dev_backup.dump`, SHA-256 `de4cc5718a7ddc0ad09fefea06eafd61792b617dfd22547f272c6f152e17d578`, 12,501,982 bytes. The local PostgreSQL role lacked `CREATEDB`, so the test used the machine's local `postgres` administrator solely to create the disposable database owned by `ubuntu`; restoration and verification ran as `ubuntu`.

To repeat the import with the exact release asset staged at the path above: `python3 tools/ceres_pg.py run --database loom_dev`. To repeat the isolated restore: `python3 tools/ceres_pg_backup_restore.py --database loom_dev`. Both fail closed if a pinned source, semantic matrix, consumer query or source column/view shape changes. The backup and original SQLite sources remain outside PostgreSQL. Development rollback can select an earlier snapshot or restore the retained dump; no production rollback is implicated because no consumer was switched.

This is a complete migration of the **existing Ceres Atlas consumer dataset and interactions**, not a claim that every WORLD/CIVSTATE record is semantically qualified or that unsupported Atlas domains have new capabilities. Gate B provenance remains `PARTIAL`, Gate C numeric/accounting qualification `NOT_TESTED`, and Gate D model replay `PARTIAL` under the reused MVP-A decision. PostgreSQL row parity and a successful restore do not close those separate gates. The Ceres application still reads SQLite, so its existing unresolved labels and claims remain a future consumer-integration concern; development PostgreSQL exposes the explicit field-status metadata needed for that integration.
