# Governed development loop

This is a procedural aid, subordinate to the repository's `AGENTS.md` and live LOOM governance. It grants no authority, approval, mutation scope, autonomous trigger, or qualification waiver. A named Codex review profile is an on-demand subagent, not a registered LOOM autonomous agent. Launch the parent in read-only mode when the review must be enforced read-only: live parent sandbox overrides can supersede a profile default. Do not create an automatic Astra role.

1. **Bootstrap live authority.** Read `LOOM_START_HERE.md`, current workstate, authority, change-control and applicable scoped `AGENTS.md` from authoritative `main`; verify branch/PR heads and local changes. Git state outranks remembered chat. If authority cannot be verified, hold authoritative mutation.
2. **Classify and bound.** State the primary change class, parent work item, governing sources, exact allowed files/actions, dependencies, frozen objects, acceptance gates, recovery path and explicit non-scope. Ask only for unresolved intent or authorization that repository evidence cannot supply.
3. **Challenge before scale-out.** Identify foundational assumptions and the smallest representative vertical slice that could falsify the architecture. For a proposed architecture/handoff, invoke the read-only `loom-preflight` profile when available. Authorize broader implementation only after the pilot passes its highest-leverage gate. A worker may discover that the specification is wrong; it may not silently repair the specification while implementing it.
4. **Execute the authorized slice.** Prefer one persistent worker session, worktree and Goal through implementation and ordinary repair. Keep the same healthy worker when debugging becomes difficult. Work within declared scope and preserve evidence, including failed results.
5. **Test the real claim.** Run local meaningful unit and relevant functional tests, then the required governance, platform, scientific or release gates. For user-facing behavior, test the supported user interaction path; privileged or test-only APIs are diagnostics, not product acceptance. Move physical device, touch, visual comprehension and human usability checks to a representative early slice when those properties matter. Deterministic checks (tests, schemas, hashes, SQL constraints, solvers, manifests and `loom-gate`) decide exact questions ahead of model opinion.
6. **Repair ordinary defects.** Failure alone is not escalation. Implementation bugs, failed tests, difficult debugging, optimization, data defects and bounded repairs remain worker responsibilities. Do not hide a failure or weaken acceptance criteria to turn it green.
7. **Escalate decisions, not defects.** Pause only the affected decision when progress requires resolving an architecture/specification contradiction, authority conflict, materially consequential unresolved design, expanded mutation scope, new or changed acceptance criteria, consequential novel scientific/engineering assumption, or action outside the worker mandate. Send `loom-integrator` a compact packet: governing sources and exact refs, current contract, observed evidence, decision needed, options and consequences, affected interfaces, acceptance impact and blocked step. Its read-only decision returns to the same worker. Escalate to a human only for genuine intent, canon, risk or authority decisions that evidence cannot settle.
8. **Deliver.** Preserve provenance and qualification evidence, run required gates, then commit/push/report when authorized. Report exact files, tests and outcomes, unresolved limits, SHA and PR state. Never merge without authorization.

For long-running work, report conditional ETA ranges at meaningful milestones using observed progress and remaining gates. Do not invent a precise wall-clock forecast before execution.

**First intended trial, separate from this setup:** Solar basemap physical Pixel closure. Use fresh `loom-preflight` review, a Mars-only pilot handoff, one persistent Luna Medium worker and Goal, physical Pixel acceptance, then scale out only after pilot PASS. Avoid compiler/product regeneration in that pilot unless preflight evidence shows it is necessary. This note does not authorize the trial.
