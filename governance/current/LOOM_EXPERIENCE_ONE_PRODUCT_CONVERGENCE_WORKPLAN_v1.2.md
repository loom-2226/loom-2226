## 0. Purpose

This update narrows the current Experience One implementation priority to one concrete product closure:

> **Make the complete Ceres → Neptune flight loop work end-to-end on the Pixel using governed deterministic machinery and persistent campaign state.**

It does not discard the broader product hypothesis in v1.0. It changes the current critical path so that new emergent-reality, relationship-anchor, NPC-persistence, motivation-engine, ABM, or drama-management work cannot expand the flight run by momentum.

The existing Ceres projection/Mara work remains valid supporting work and evidence. It should not be extended into a generalized motivation architecture as a prerequisite for the first full flight.

Where v1.2 conflicts with v1.0/v1.1 on current sequencing or E1-required scope, v1.2 controls. v1.1 still controls diagnostic and PASS/falsifier semantics.

# 1. Current finish line

Experience One closes when a user can complete this governed path:

```text
START AT / NEAR CERES
        ↓
ORIENT ENOUGH TO UNDERSTAND CURRENT PLACE / SHIP
        ↓
FORM OR EXPRESS NEPTUNE INTENT
        ↓
DETERMINISTIC NAVIGATOR PRODUCES VALID ROUTE OPTIONS
        ↓
USER CAN INSPECT / COMPARE QUALIFIED DIMENSIONS
        ↓
USER EXPLICITLY SELECTS + AUTHORIZES ONE OPTION
        ↓
GOVERNED EXECUTION / CAMPAIGN COMMIT OCCURS
        ↓
WAYFARER ARRIVES AT NEPTUNE
        ↓
PERSISTENT CAMPAIGN HISTORY RECORDS THE JOURNEY
        ↓
PROCESS / APP RESTART STILL RESOLVES WAYFARER AT NEPTUNE
        ↓
MINIMAL NEPTUNE ORIENTATION ANSWERS “WHERE AM I / WHAT IS THIS PLACE?”
```

This is the current E1 production finish line.

The run does **not** require LOOM to generate a second mission, spontaneous local conflict, persistent new NPC, or broad institutional consequence after arrival.

# 2. Required current capabilities

For this phase, the four v1.0 capabilities are interpreted narrowly.

## 2.1 PLACE — minimum required

At Ceres, the user can determine:

- Wayfarer identity;
- current location/context;
- current campaign/epoch context required to understand the flight;
- enough local context that Neptune intent is not issued from a blank prompt.

Existing read-only Canon Context Projection/Mara work may satisfy this requirement where empirically demonstrated.

No generalized local-society simulation is required.

## 2.2 TEXTURE — minimum required

Texture is sufficient for this run when Ceres and Neptune are demonstrably real places in existing governed LOOM data/canon and the user can interrogate enough of that context to understand departure and arrival.

Texture does not require a procedurally generated motivation hook.

Existing projection/synthesis/presentation work should be reused; do not replace it merely to deepen texture.

## 2.3 AGENCY — full flight requirement

The user can express a Neptune flight intent, including a bounded qualifier such as speed/reserve where the current qualified machinery supports it.

Mara/model input must resolve into typed deterministic planning requests. The model may interpret/explain; Navigator and governed services own calculations.

The system must expose multiple route options where the qualified E1 path requires them, using deterministic/reproducible candidate generation and only qualified comparison dimensions.

## 2.4 CONSEQUENCE — full flight requirement

After explicit user authorization:

- the selected plan crosses the governed execution boundary;
- campaign authority records the committed journey;
- arrival state becomes Neptune through the authoritative campaign path;
- history/provenance survive restart;
- browser/session/model context is not required to reconstruct the result.

For v1.2, this persistent flight consequence is sufficient.

# 3. Current critical path

The implementation order is now:

## F0 — close prerequisite governance/evidence debt

Close only the baseline/evidence obligations required to replace or integrate current flight behavior honestly, including G1 where applicable.

Do not expand G1 into a documentation project detached from the actual flight seams.

## F1 — freeze the known-good Ceres orientation path

Use the smallest empirically demonstrated Ceres place/context path already available.

Required question:

> Can the user tell where Wayfarer is and what Ceres is without relying on invented model knowledge?

Once sufficient, stop extending Ceres motivation/texture for E1.

## F2 — integrate Neptune intent → deterministic route alternatives

Move from user/Mara intent to typed Navigator planning.

Required properties:

- no prose coordinates/trajectory authority;
- fixed input state and solver version reproduce route candidates/order within declared tolerance;
- candidate metrics shown to the user are qualified;
- planning remains non-mutating.

## F3 — compare / preview / select

The player can inspect alternatives using existing HUD/Nav/GIS capabilities where practical.

Required minimum actions:

- `SHOW ROUTE`
- `COMPARE`
- `WHY`
- select candidate

Playback/preview should reuse authoritative sampled/path output and existing browser-presentation boundaries. Do not create browser flight physics.

## F4 — explicit authorization + governed handoff

The chosen candidate must cross the existing typed validation/execution boundary.

Required properties:

- stale state fails closed;
- final authorization is explicit user action;
- Mara/LLM cannot final-authorize;
- no alternate LLM-specific flight execution path;
- the handoff object between plan/execution/campaign commit is explicit and testable.

## F5 — execute / commit / arrive

Close the seam between qualification/local execution semantics and persistent campaign flight state.

Required evidence:

- a real Ceres → Neptune run or qualification-equivalent governed execution path;
- `FLIGHT_COMMITTED` / arrival semantics as required by current Navigator authority;
- authoritative post-flight location resolves to Neptune;
- history contains sufficient provenance to explain how the state was reached.

## F6 — restart persistence

Kill/restart the relevant process/app/runtime and reload campaign state.

PASS requires:

- Neptune remains authoritative current location;
- committed journey is recoverable from persisted state/history;
- no reconstruction from browser memory, chat history, or model context.

## F7 — minimal Neptune arrival orientation

Provide enough governed/read-only context to answer:

- **Where am I?**
- **What is this place?**

This may reuse the Canon Context Projection pattern. It does not require a new Neptune storyline or emergent motivation system.

## F8 — Pixel zero-instruction end-to-end run

Hand the Pixel to a user with the minimal premise:

> **You’re aboard Wayfarer. Explore.**

For the current run, success means the user can reach and complete the Ceres → Neptune action loop with no developer intervention beyond defects/environment setup that would also affect a normal deployment.

# 7. Gate interpretation for this scoped run

Existing v1.0/v1.1 gates remain authoritative where applicable, but current review should report them against the flight closure above.

The most important practical PASS claims are:

### Flight planning PASS

A fixed Ceres/Wayfarer/epoch/constraint state produces valid deterministic Neptune candidate plan(s) and reproducible ranking where ranking is exposed.

### Flight selection/authorization PASS

The selected plan remains tied to current authoritative state and cannot execute after invalidating state changes; explicit user authorization is required.

### Flight execution/commit PASS

The authorized plan reaches the campaign commit path without an ungoverned shadow executor or narrative substitution.

### Arrival PASS

Authoritative campaign state resolves Wayfarer at Neptune and records the journey.

### Restart PASS

The post-flight Neptune state and journey provenance survive restart without browser/model/chat memory.

### Neptune orientation PASS

The user can retrieve minimal grounded arrival context from governed data/projection.

Each PASS remains subject to v1.1 evidence maturity, exact reference, target configuration, limits, and falsifier requirements.

# 8. Explicit deferrals

- a living autonomous Ceres simulation;
- a living autonomous Neptune simulation;
- a generated quest;
- a persistent newly generated NPC;
- political/economic CIVSTATE consequences of the flight;
- a generalized relationship graph runtime;
- full conversational GM behavior;
- generalized social simulation;
- production adoption of Research Lab emergent-reality work;
- a new renderer where an existing renderer can close the flight;
- new ship design/optimization work unrelated to flight closure.

These may become later product/research work, but they may not block this run merely because they would improve the universe.

# 9. Product boundary after Neptune

The current product split is:

## Experience One

> **Can I go somewhere?**

Ceres → understand enough context → form Neptune intent → deterministic options → compare → authorize → fly → arrive → persist → orient at Neptune.

## Candidate next experience / research question

> **Now that I am here, why does anything matter to me?**

That second question is where persistent relationship anchors, emergent situations, consequential NPC promotion, and LLM GM improvisation may earn production scope after research falsification.

Do not solve the second question by delaying the first.
